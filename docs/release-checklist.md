# 发布前检查清单

此清单用于准备版本标签、安装包或 GitHub Release。以**将要发布的提交**为准逐项核对，记录实际结果；构建通过不等于发布完成。

## 1. 版本与内容

- 比较上一个发布标签与本次提交，核对重要功能、行为变化和已知限制；发布说明用用户能理解的语言写清改动，不只列提交标题。
- 发布说明采用 [固定模板](releases/TEMPLATE.md)：保留 `## 更新摘要` 与 `## Update summary` 两个标题，各 1–6 条单行 `- ` 列表，中文每条不超过 80 字符、英文不超过 180 字符。摘要仅写用户可见改动，不用粗体、链接、图片、嵌套列表、版本标题或测试日志；重要不兼容变更应占一条摘要。安装要求、支持限制与测试结果放在后续完整说明中。更新弹窗按界面语言展示摘要，其他语言回退英文，完整内容由“完整发布说明”打开对应版本的 GitHub 页面。
- 摘要优先写用户必须采取的升级操作和主要收益；正文按升级须知、主要改进、行为变化与修复、安装兼容性与已知限制组织。完整说明中英文分块，逐步操作链接到对应版本手册；截图仅在有助于理解本版变化时添加。技术原因与详细测试记录放在验收文档。
- 修订旧版说明只调整结构和纠正事实，不加入标签之外的功能，不覆盖旧附件；新版说明与旧版说明分别核对。
- 发布前运行 `.venv/bin/python scripts/check_release_notes.py docs/releases/vX.Y.Z.md`；格式校验失败先修正，不发布。弹窗检查包含中英文、三种主题、长摘要滚动，以及关闭再打开时从首条显示。尚未支持摘要的旧版客户端仍会原样显示完整 Release 正文；修订说明文字不会改变这些已安装客户端的界面。
- 检查 `pyproject.toml` 版本、应用内版本、标签 `v<版本>` 和安装包文件名一致。
- 运行相关回归与完整测试；对影像、分割、测量、工作区等高风险变化做实际界面与文件往返验证。

## 2. README 与截图

- 审核本次是否修改重要界面或操作流程。逐项检查中英文 README、[界面图集](screenshots/README.md)及操作动画：旧版本号、旧控件位置、已合并或拆分的功能、失效说明都需要更新。用当前提交运行应用重新截图或录制动画，并检查画面清晰、无私有患者信息。
- 两版 README 应概括**整个软件**的当前功能，功能名称、限制、截图和语言切换链接保持一致。不要写影像数据来源、获取或复现链接。
- 检查所有本地图片和文档链接存在。下载链接必须指向本次最新 Release 的**实际附件名**；发布后再次打开链接核验，不能只替换版本号。
- 截图优先读取应用自身窗口内容，禁止直接用桌面区域截取工作区对话框；逐张、逐帧检查聊天窗口、手机镜像、通知和其他应用覆盖。发现污染素材时重新截取，并同步替换 README、首页与手册引用；使用新文件名避免旧图缓存。

## 3. 平台产物

- **macOS：本地 Mac 打包**，使用 `bash scripts/build_macos.sh`。校验 `.app`、DMG、架构、版本、签名及启动和核心阅片流程；生成 SHA-256，将 DMG 与校验文件上传到对应 Release。
- macOS 正式签名分发使用 `bash scripts/build_macos.sh --release`，提前配置 `MACOS_SIGN_IDENTITY` 和 `MACOS_NOTARY_PROFILE`（见[配置说明](macos-signing.md)）。核对应用及 DMG 公证状态均为 Accepted、票据验证和 Gatekeeper 检查通过；票据装订后再生成 SHA-256。缺少证书或公证失败不得当作正式签名包发布；历史版本的 ad-hoc 验证记录不代表新包通过。首次启用签名后，在另一台 Mac 上下载、断网安装并启动，抽查 QML、2D、3D、文件访问及更新替换。
- **Windows：GitHub Actions 构建与发布**，使用 `.github/workflows/build-windows.yml` 的标签或 `release_tag` 流程。确认该运行检出的提交与标签一致、测试通过，再核对安装版、便携版及两份 SHA-256 附件。不要用本地 Mac 包代替 Windows 产物。构建附件内的 `windows-provenance.json` 记录实际检出 SHA、版本、运行 ID 和包哈希；归档时必须与标签提交及下载文件一致，旧构建缺少清单时应重新构建。公开 Release 仅允许核验同名文件大小和 SHA-256 完全一致后无操作结束，缺失或不同则失败；上传及替换只允许对草稿执行。上传期间不要同时手动公开草稿（GitHub 的状态读取和附件上传不是原子操作）。
- 使用 `docs/packaging.md` 的平台说明核对安装、启动和更新；无法在目标系统验证的项目要如实写在发布说明中。
- 不要通过重跑旧运行来绕过上述发布校验：历史运行保留当时的工作流定义。归档旧版本应从包含这些保护的新工作流发起 `release_tag`，并按清单重新构建、核验；不能继续使用缺少保护的历史上传步骤。
- 自动更新验收：在已安装的上一版中验证启动检查、更新内容、取消同一版本后不再弹窗及版本号更新标识；关闭自动检查并重启应不联网检查。测试下载中断、校验失败、工作区保存/取消退出。macOS 验证 DMG 替换和重新启动；Windows 安装版与单文件便携版分别验证更新、启动和失败恢复，用户设置及工作区不得丢失。

- 升级包验收基线由 `tests/fixtures/upgrades/windows-baseline-v2.5.0.json` 固定旧标签、附件大小和 SHA-256；更换基线需显式审核，不能读取 mutable latest 后因版本相同而跳过。候选版本必须高于基线。Windows 安装版与便携版都需生成 `package-upgrade.json` 和各自 `workspace-restored.json`，用实际新包恢复旧版本保存的非空合成工作区，核对图像像素、测量、QA、CPR 及迁移设置。
- 安装迁移、当前更新辅助程序、旧客户端“更新”按钮是不同验收范围，分别记录。2.5.0→2.6.0 更名走手动安装迁移；自动脚本明确记录旧客户端按钮 `not_exercised`，不能把包启动/辅助程序成功写成旧客户端更新通过。原生及外部数据验收的跳过项需列出原因；必测阶段不得以跳过算通过。

## 4. 发布后核验

- 核对 GitHub Release 的标签、提交、发布说明、六个预期附件及 SHA-256；确认发布状态和最新版本页正确。
- 正式发布前将三个安装包及其 SHA-256 全部上传到草稿 Release，再公开发布；自动更新读取最新正式 Release 的说明和平台附件。附件名、版本、校验文件名必须一致，不要修改已发布版本的包内容。首个带更新功能的版本需用户手动安装一次。
- 打开 README 中 macOS / Windows 下载链接、语言切换链接及主要截图链接，确认它们指向刚发布的版本。
- 六个附件上传完成后，更新 `docs/manual-site/release.json` 的版本与三个安装包文件名；确认网站首页的 macOS / Windows 直链与版本号一致，并触发网站重新部署。不要在附件可下载前切换首页版本。
- 发布结果列出版本、测试和平台验证情况；如某项未通过或未执行，说明原因与影响。
